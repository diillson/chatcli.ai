<ParamField path="name" type="string" required>
  PostMortem name (e.g., `pm-checkout-service-oom-kill-1773871200`)
</ParamField>

<ParamField query="namespace" type="string" default="default">
  Kubernetes namespace (only `default` is searched when omitted)
</ParamField>

<ParamField body="acknowledgedBy" type="string">
  Who performed the follow-up. Maximum 253 characters. Stored in the annotation `aiops.chatcli.io/human-action-acknowledged-by`.
</ParamField>

<ParamField body="note" type="string">
  Free-text note about what was done. Maximum 1024 characters. Stored in the annotation `aiops.chatcli.io/human-action-note`.
</ParamField>

## When to Use

When the operator **contains** an incident (for example, it silences a crashing workload instead of fixing it), the Issue ends in state `Contained` and its PostMortem gets `requiresHumanAction: true` plus a `requiredAction` describing what a person must do. While that flag is set and not acknowledged, the PostMortem controller reverts any `Closed` state back to `Open`.

After doing the follow-up, call this endpoint. It:

1. Sets the annotations `aiops.chatcli.io/human-action-acknowledged: "true"` and `aiops.chatcli.io/human-action-acknowledged-at` (UTC, RFC 3339), plus `-acknowledged-by` and `human-action-note` when sent
2. Clears `status.requiresHumanAction` (`requiredAction` is kept as history)

Then [close the postmortem](/reference/api/close-postmortem). The body is optional. Minimum role: `operator`.

<Note>
The call does not restore the workload itself; it only records that someone did. Setting the annotation with `kubectl annotate` has the same effect on the controller (values `true`, `True`, `yes`, `ack` and `acknowledged` are accepted), but leaves `status.requiresHumanAction` set.
</Note>
