description: "Manually resolves an incident — used when the platform escalates to human action or when an operator confirms the issue is fixed"
icon: "circle-check"
---

<ParamField path="name" type="string" required>
  Name of the Issue resource (e.g., `payment-service-oom-kill-1773933600`)
</ParamField>

<ParamField query="namespace" type="string">
  Namespace of the incident. When omitted, every namespace is searched and the first incident with that name is resolved — pass it explicitly when names can repeat across namespaces.
</ParamField>

<ParamField body="resolution" type="string">
  Description of how the incident was resolved. If omitted (or the body is empty), defaults to `"Manually resolved via dashboard"`.

  Best practice: always provide a meaningful resolution message for the audit trail.
</ParamField>

## When to Use This Endpoint

### 1. Escalated Incidents (Human Action Required)

When automatic remediation is exhausted — `maxRemediationAttempts` attempts (Instance `spec.aiops.maxRemediationAttempts`, default 5, or the matching Runbook's `maxAttempts`) — the incident moves to **Escalated**. From there:

- Configured notification and escalation policies alert the on-call team
- **No further automatic remediation is attempted**
- If auto-resolve is enabled (Instance `spec.aiops.enableAutoResolve`, default `true`), the operator re-checks the resource every 30 seconds and resolves the incident itself once all replicas are healthy
- Otherwise the incident stays `Escalated` until someone resolves it through this endpoint or the web dashboard

### 2. Manual Verification After Auto-Remediation

Even when automatic remediation succeeds, operators may want to close the incident with their own resolution text.

### 3. False Positives

When an incident turns out to be a false positive, resolve it with a resolution such as `"False positive — metric spike caused by scheduled batch job"`.

## Resolution Flow for Escalated Incidents

```
Incident Detected
      ↓
  AI Analysis → Runbook/Agentic Remediation
      ↓                    ↓
  Success → Resolved    Failure (retry up to maxRemediationAttempts)
                           ↓
                    All attempts exhausted
                           ↓
                      ESCALATED ← You are here
                           ↓
         ┌─────────────────┼──────────────────┐
         ↓                 ↓                  ↓
    API Resolve      Dashboard button    Auto-resolve
  POST /resolve        "Resolve"       (resource healthy)
         ↓                 ↓                  ↓
         └─────────────────┼──────────────────┘
                           ↓
                    State: Resolved
```

## What Happens on Resolution

1. **State change**: any state except `Resolved` (including `Escalated`, `Failed` and in-progress states) becomes `Resolved`; `status.resolution` and `status.resolvedAt` are set. Resolving an already resolved incident returns `409`.
2. **Annotations added**:
   - `aiops.chatcli.io/resolved-by` — the **role** of the calling API key (`operator` or `admin`)
   - `aiops.chatcli.io/resolved-at` — resolution timestamp
   - `aiops.chatcli.io/manual-resolution` — `"true"`
3. `Resolved` is terminal: the Issue controller stops processing the incident.

<Warning>
A manual resolve does **not**: generate a PostMortem (PostMortems are created only when a RemediationPlan finishes), record an AuditEvent, stop a RemediationPlan that is already running, or clear the watcher's deduplication entry for the resource (the hook exists but is not wired in the operator), so a recurring anomaly on the same resource can stay deduplicated until the entry expires (Instance `spec.aiops.dedupTTLMinutes`, default 30).
</Warning>
