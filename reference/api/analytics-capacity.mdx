---
title: "Analytics Capacity"
openapi: "GET /analytics/capacity"
description: "Returns a requests-versus-limits capacity report for Deployments that had incidents"
icon: "server"
---

<ParamField query="namespace" type="string">
  Filter by Kubernetes namespace. Omit it to cover every namespace.
</ParamField>

<ParamField query="from" type="string">
  Start of the window, RFC 3339.
</ParamField>

<ParamField query="to" type="string">
  End of the window, RFC 3339. The window **length** is `to − from` when both are valid, otherwise 7 days; the window always ends at the current time.
</ParamField>

Minimum role: `viewer`. One forecast is built for each distinct resource referenced by an Issue (any Issue, not only those in the window). The planner reads it as a **Deployment** of that name; resources that are not Deployments, or that no longer exist, are skipped silently.

## Forecast Fields

| Field | Description |
|-------|-------------|
| `Resource` | The resource the Issues point at (`kind`, `name`, `namespace`) |
| `CurrentUsage` | Requests of the first container, used as a proxy for usage (`CPUMillicores`, `MemoryBytes`); not live metrics |
| `Limits` | Limits of the first container |
| `UsagePercentage` | `CurrentUsage / Limits × 100` for `CPU` and `Memory` |
| `Trend` | `Direction` is `insufficient_history` and the per-day slopes are `0`: the operator keeps no usage history to fit a trend |
| `Forecast` | A `Recommendation` string; the exhaustion dates are `null` and the day counts `0`, since no exhaustion date is projected |
| `IncidentCorrelation` | Issues in the namespace inside the window, how many target this resource, and `ResourceIsBottleneck` (more than 2) |
| `UsageSource` | Where `CurrentUsage` comes from: always `requests` |
| `HistoryAvailable` | Always `false`: no usage samples are collected |
| `Urgency` | `plan` when requests reach 80% of limits or the resource is a bottleneck, `none` otherwise |

The recommendation warns when requests are above 80% of limits, then flags repeated incidents on a bottleneck resource, and otherwise says that no trend can be projected and requests are within limits.

<Warning>
This is a requests-versus-limits report plus incident correlation, not a forecast: usage is what the first container requests, not measured consumption, and no trend or exhaustion date is projected.
</Warning>

<Note>
The forecast is a Go struct with no JSON tags, so its keys are **PascalCase** (only `Resource` keeps lowercase inner keys). Absent exhaustion dates are `null` and absent day counts are `0`.
</Note>
