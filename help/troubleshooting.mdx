Found a problem? This page lists the most common errors and how to fix them.

<Tip>
For more detailed diagnostics, enable debug logging: `LOG_LEVEL=debug chatcli`
</Tip>

## Common Problems

<AccordionGroup>
  <Accordion title="chatcli command not found" icon="terminal">
    **Symptoms:** `bash: chatcli: command not found` or `zsh: command not found: chatcli`.

    **Cause:** The Go binary directory is not in your system's `PATH`.

    **Solution:**

    1. Open your shell configuration file (`~/.bashrc`, `~/.zshrc`, etc.)
    2. Add the following to the end of the file:
    ```bash
    export PATH=$PATH:$(go env GOPATH)/bin
    ```
    3. Restart your terminal or run `source ~/.zshrc`
  </Accordion>

  <Accordion title='Error "No LLM provider is configured"' icon="key">
    **Symptoms:** ChatCLI terminates immediately after starting.

    **Cause:** No API key has been configured in the `.env` file.

    **Solution:**

    1. Create or open the `.env` file in the directory where you run `chatcli` (or in your `HOME`)
    2. Add credentials for at least one provider:
    ```env
    LLM_PROVIDER=OPENAI
    OPENAI_API_KEY="sk-your-secret-key-here"
    ```
    3. Save and run `chatcli` again
  </Accordion>

  <Accordion title="Changes to .env have no effect" icon="rotate">
    **Symptoms:** You changed `LLM_PROVIDER` or another value, but ChatCLI uses the old configuration.

    **Cause:** ChatCLI loads configuration at startup.

    **Solution:** Use the `/reload` command within interactive mode to reload variables instantly.

    ```bash
    /reload
    ```
  </Accordion>

  <Accordion title="@file cannot find a file/directory" icon="file-circle-exclamation">
    **Symptoms:** Error "file does not exist" or "path not found".

    **Solution:**

    - **Relative Paths** -- are relative to the directory where you ran `chatcli`. E.g.: `@file ./project/src/main.go`
    - **Home (`~`)** -- works as a shortcut: `@file ~/documents/notes.txt`
    - **Permissions** -- check with `ls -l` that you have read permission on the file
  </Accordion>

  <Accordion title="Agent Mode does not execute anything" icon="robot">
    **Symptoms:** The AI presents an action plan but just waits without executing.

    **Cause:** This is the expected behavior! Agent Mode requires explicit approval.

    **Solution:**

    - Type the command **number** (e.g., `1`) to execute it individually
    - Type `a` to execute **all** commands in sequence
    - Use `--agent-auto-exec` in one-shot mode for automatic execution of safe commands
  </Accordion>

  <Accordion title="Ollama provider is not detected" icon="server">
    **Symptoms:** Even with `OLLAMA_ENABLED=true`, the provider does not appear available.

    **Solution:**

    1. **Ollama Server** -- confirm it is running: `ollama serve`
    2. **Model downloaded** -- check with `ollama list`. If empty, download one: `ollama pull llama3`
    3. **Base URL** -- if not at the default address, set it in the `.env`:
    ```env
    OLLAMA_BASE_URL="http://localhost:11434"
    ```
  </Accordion>

  <Accordion title="Truncated or incomplete responses" icon="scissors">
    **Symptoms:** The AI response stops in the middle of a sentence.

    **Cause:** The response token limit was reached.

    **Solution:** Increase the `MAX_TOKENS` for your provider in the `.env`:

    ```env
    OPENAI_MAX_TOKENS=60000
    ANTHROPIC_MAX_TOKENS=20000
    GOOGLEAI_MAX_TOKENS=50000
    ```
  </Accordion>

  <Accordion title="API call timeout" icon="clock">
    **Symptoms:** Timeout error or the application hangs waiting for a response.

    **Solution:**

    - Use `--timeout` to set a limit: `chatcli -p "question" --timeout 60s`
    - Configure `MAX_RETRIES` and `INITIAL_BACKOFF` in the `.env` for automatic retries
    - Consider configuring [Provider Fallback](/providers/provider-fallback) for redundancy
  </Accordion>

  <Accordion title="Agent needs to create a temporary file but /coder blocks it">
    `/coder` mode validates that every write happens inside the project directory. Starting with this release, ChatCLI creates a [Session Workspace](/context/session-workspace) at `$TMPDIR/chatcli-agent-<random>/` that is automatically on the allowlist:

    ```xml
    <tool_call name="@coder" args='{"cmd":"exec","args":{"cmd":"cat > $CHATCLI_AGENT_TMPDIR/script.sh <<EOF\n...\nEOF\nbash $CHATCLI_AGENT_TMPDIR/script.sh"}}' />
    ```

    For writes via `write` or `patch`, use the absolute path that appears in the system prompt (the `$CHATCLI_AGENT_TMPDIR` variable is not expanded inside the `file` argument).

    Cleanup runs automatically on exit; set `CHATCLI_AGENT_KEEP_TMPDIR=true` to preserve and inspect.
  </Accordion>

  <Accordion title="Tool result truncated but I cannot see the full content">
    When the budget cuts an output and shows `[full output saved to /tmp/chatcli-agent-XXX/tool-results/...]`, the path is on the agent's read allowlist. Just open it with `read_file`:

    ```xml
    <tool_call name="@coder" args='{"cmd":"read","args":{"file":"/tmp/chatcli-agent-XXX/tool-results/budget_tc_3_1.txt","start":1200,"end":1500}}' />
    ```

    Do not re-run the original tool call — the content is already on disk. Details in [Tool Result Management](/context/tool-result-management).
  </Accordion>

  <Accordion title="A /metrics endpoint or huge log saturates the context">
    Two complementary strategies:

    1. **`@webfetch` filters** — pass `filter`, `exclude`, `from_line`/`to_line` to filter before truncation, or `save_to_file: true` to persist the body to the scratch dir and read slices later with `read_file`. See [Web Tools](/tools/web-tools#filters-for-large-payloads).
    2. **Subagent delegation** — `delegate_subagent` runs the analysis in an isolated context window and returns only the summary. See [Subagent Delegation](/agents/subagent-delegation).
  </Accordion>

  <Accordion title="Subagent refuses to run with 'subagent depth N exceeds maximum'">
    You reached the nested-delegation limit (default 2). Common cause: a subagent delegating to another subagent in a loop. Increase carefully:

    ```bash
    CHATCLI_AGENT_SUBAGENT_MAX_DEPTH=3 chatcli
    ```

    But consider whether the task wouldn't fit better in a single delegation with a more explicit `prompt` about what needs to be done.
  </Accordion>
</AccordionGroup>

## Encrypted data: protect it and recover it

Your sessions, memory and other local data are [encrypted at rest](/security/encryption-at-rest) by default. Encryption means the key matters: these scenarios cover how not to lose access and how to get it back.

<Warning>
**Three rules that prevent almost every loss:**
1. Run `/config security recovery-key` once and keep the key in a password manager.
2. Never edit or delete files under `~/.chatcli` by hand to "fix" an error, and never delete the `chatcli` / `auth-key` item from the OS keychain or the `~/.chatcli/.auth-key*` files.
3. Back up `~/.chatcli` like any other data. A backup is only useful together with the recovery key, so keep them apart.
</Warning>

<AccordionGroup>
  <Accordion title='"encrypted at rest but CHATCLI_ENCRYPTION_KEY is not set" or "Locked stores"' icon="lock">
    **Cause:** ChatCLI could not read the key. The error says why, for example a locked macOS keychain in an SSH session, or Linux with `secret-tool` but no desktop session. `/config security` shows `unavailable` with the reason.

    **What happens meanwhile:** nothing is lost. Memory stores that cannot be opened are locked read-only so nothing overwrites them, and sessions fail to load instead of loading empty.

    **Fix:** unlock the keychain (log in to the desktop, or `security unlock-keychain` on macOS) and run ChatCLI again. Where there is never a keychain, set `CHATCLI_ENCRYPTION_KEY` to your recovery key.
  </Accordion>

  <Accordion title="New machine, reinstalled system or reset keychain" icon="laptop">
    The default key lived in the old keychain. Copy `~/.chatcli` to the new machine, then:

    ```bash
    export CHATCLI_ENCRYPTION_KEY="<recovery key>"
    ```

    Everything opens. Then run `/config security use-keychain`: your data moves to the new machine's keychain key, and you can remove the variable.

    With a recovery file instead, a single command does both: `/config security recovery-key --restore <file>` (it asks for the file's passphrase).

    **Without a recovery key and without the old keychain, the encrypted stores cannot be recovered.** That is the point of encryption. Exports you made earlier (`/session export`, `/memory export`) are plaintext and still import.
  </Accordion>

  <Accordion title='Cron, SSH or a container: "the credential key of this installation lives in the OS keychain"' icon="clock">
    After the key moved to the keychain, ChatCLI refuses to create a new one in a context that cannot reach the keychain, because a new key would orphan your data. Give that context the key instead:

    ```bash
    CHATCLI_ENCRYPTION_KEY="<recovery key>" chatcli -p "..."
    ```

    Do not delete `~/.chatcli/.auth-key.keychain` to make the error go away: it is what stops a second key from being created.
  </Accordion>

  <Accordion title="Going back to an older ChatCLI version" icon="clock-rotate-left">
    Older versions cannot read encrypted stores. With the **new** version, first write everything back in plaintext:

    ```bash
    export CHATCLI_ENCRYPTION_KEY=off
    chatcli    # then run: /config security reseal
    ```

    Then install the older version. Keep `CHATCLI_ENCRYPTION_KEY=off` if you use the new version again.
  </Accordion>

  <Accordion title="Turning encryption off" icon="toggle-off">
    `export CHATCLI_ENCRYPTION_KEY=off` stops encrypting new data. Data already encrypted keeps opening. To also decrypt what exists, run `/config security reseal` while it is off.
  </Accordion>

  <Accordion title="A restored backup brought back an old .auth-key" icon="box-archive">
    Once the key is in the keychain, a key file that shows up later is ignored in favor of the keychain key, with a warning. Nothing is overwritten. Remove the stray `~/.chatcli/.auth-key` when you have confirmed `/config security` shows the keychain key.
  </Accordion>

  <Accordion title="I edited an encrypted file, or a file is damaged" icon="file-circle-xmark">
    Encrypted files are authenticated: a changed byte makes the whole file fail to open. ChatCLI never treats it as empty and never overwrites it.

    - Restore that file from a backup.
    - Daily notes are the exception you can edit: a note saved in plaintext by hand still reads, and is encrypted again on the next write.
    - To read or change your data outside ChatCLI, export it first (`/session export`, `/memory export`, `/context export`).
  </Accordion>

  <Accordion title='"the OS keychain holds a different credential key than ~/.chatcli/.auth-key"' icon="key">
    **Cause:** the OS keychain already holds a `chatcli` / `auth-key` item that is not your key (often left there by an older build or a test run), while your real key is the file `~/.chatcli/.auth-key`. ChatCLI never overwrites a keychain key on a guess, so it keeps using the file: your data, credentials and recovery key are not affected.

    **Fix:** run `/config security use-keychain`. It moves the file key into the keychain only after checking that it opens your credential store, keeps the keychain's previous value as `auth-key.previous`, and reads the key back before removing the file. The key itself does not change, and the warning stops.
  </Accordion>

  <Accordion title="Switching CHATCLI_KEYCHAIN_BACKEND between keychain and file" icon="key">
    Safe in both directions: the key is the same, only where it is kept changes. Switching to `file` copies the key from the keychain into `~/.chatcli/.auth-key` (mode `0600`) and keeps the keychain item; switching back to `keychain` or `auto` uses the keychain again. The only thing to keep in mind is that with `file` the key sits on disk next to the data.
  </Accordion>

  <Accordion title="Using the same data on two machines" icon="arrows-left-right">
    The keychain key belongs to one machine. Set the same `CHATCLI_ENCRYPTION_KEY` on both (for example your recovery key from the first one), run `/config security reseal` once on each, and copy or sync `~/.chatcli` between them.
  </Accordion>
</AccordionGroup>
