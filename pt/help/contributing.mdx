Contribuições são bem-vindas, de um erro de digitação nesta documentação a um provider novo ou uma capacidade de agente. O ChatCLI é open source sob a **Apache License 2.0**, e todos que participam seguem o [Código de Conduta](https://github.com/diillson/chatcli/blob/main/CODE_OF_CONDUCT.md).

O guia completo fica no repositório: [CONTRIBUTING.md](https://github.com/diillson/chatcli/blob/main/CONTRIBUTING.md). Esta página resume.

<Warning>
**Encontrou um problema de segurança?** Não abra issue nem pull request. Reporte de forma privada como descrito no [SECURITY.md](https://github.com/diillson/chatcli/blob/main/SECURITY.md).
</Warning>

## Setup

Você precisa do Go na versão do `go.mod`, do golangci-lint v2 e do git.

```bash
git clone https://github.com/<voce>/chatcli.git
cd chatcli
make build          # bin/chatcli, com informação de versão
go test ./...       # a suíte inteira; nunca toca o seu ~/.chatcli real
make lint           # golangci-lint run
```

Para testar seu build com um modelo, faça login no prompt com `/auth login <provider>` ou coloque uma API key num arquivo `.env` (veja [Instalação](/pt/start/installation)). O operator do Kubernetes é um módulo Go separado: rode os testes dele dentro de `operator/`.

## Fazendo uma mudança

1. Crie a branch a partir da `main` (a `develop` é um espelho sincronizado automaticamente).
2. Escreva a mudança e os testes. Uma correção de bug vem com um teste que falha sem ela.
3. Rode `gofmt -w`, `make lint` e `go test ./...`.
4. Abra um pull request contra a `main` com título no padrão [Conventional Commits](https://www.conventionalcommits.org/). Os pull requests entram por squash, e as releases são cortadas pelos mantenedores com o release-please.

Mudanças maiores (um provider novo, uma tool builtin, uma superfície nova, mudança de padrão ou de comportamento de segurança) começam com uma issue para combinar a abordagem.

## Convenções

| Área | Regra |
|---|---|
| Código Go | `gofmt`; `golangci-lint` sem issues e sem `//nolint`; cabeçalho de licença em arquivos novos; nada de `TODO`, `FIXME`, `panic` ou segredos em código de produção novo; funções novas com complexidade ciclomática até 30 |
| API pública | nunca remova nem altere uma declaração exportada: crie uma nova e mantenha a antiga delegando |
| Dependências | dependência nova precisa de aprovação dos mantenedores |
| Texto para o usuário | via `i18n.T`, em `en`, `en-US` e `pt-BR`, num arquivo de fragmento `i18n/locales/<tag>.<feature>.json` |
| Texto para o modelo | system prompts e descrições de tools ficam em inglês |
| Providers | uma capacidade é esperada em todo provider que possa suportá-la; um provider novo passa por todos os pontos da [matriz de paridade](https://github.com/diillson/chatcli/blob/main/tools/qg/providerparity/providers.go) |
| Tools builtin | versão semântica em `Version()`, com bump sempre que o que o modelo vê mudar (patch, minor, major); o `TestBuiltinVersions` garante |
| Testes | herméticos: nada grava no `~/.chatcli` real; pacotes que tocam o store da home usam `testenv.Main` |
| Commits | Conventional Commits com um único tipo; sem trailers `Co-Authored-By` |
| Documentação | este site tem cada página em inglês e português: altere as duas |

## O que o CI verifica

Todo pull request roda um quality gate com 15 floors:
- build e análise estática;
- cobertura que não pode cair, com 60% para código novo;
- sinais de código gerado por IA;
- tamanho do PR;
- testes end-to-end;
- lint de commits;
- complexidade;
- varredura de segredos;
- paridade de i18n;
- drift de CRD;
- cabeçalhos de licença;
- quebras de API;
- tamanho do binário;
- paridade de providers.

Os scans de segurança (`govulncheck`, `gosec`, CodeQL, Trivy e dependency review) também rodam. A tabela do [CONTRIBUTING.md](https://github.com/diillson/chatcli/blob/main/CONTRIBUTING.md#what-ci-checks) traz o limite de cada floor.

## Reportando bugs

Abra uma [issue no GitHub](https://github.com/diillson/chatcli/issues) com:

- a versão do ChatCLI (`chatcli --version`), o sistema operacional, o provider e o modelo;
- os passos para reproduzir, o comportamento esperado e o observado;
- logs relevantes (`LOG_LEVEL=debug`), sem segredos.
