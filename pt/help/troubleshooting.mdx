## Problemas Comuns

<AccordionGroup>
  <Accordion title="Comando chatcli não encontrado" icon="terminal">
    **Sintomas:** `bash: chatcli: command not found` ou `zsh: command not found: chatcli`.

    **Causa:** O diretório de binários do Go não está no `PATH` do seu sistema.

    **Solução:**

    1. Abra seu arquivo de configuração de shell (`~/.bashrc`, `~/.zshrc`, etc.)
    2. Adicione ao final do arquivo:
    ```bash
    export PATH=$PATH:$(go env GOPATH)/bin
    ```
    3. Reinicie seu terminal ou execute `source ~/.zshrc`
  </Accordion>

  <Accordion title='Erro "Nenhum provedor LLM está configurado"' icon="key">
    **Sintomas:** O ChatCLI encerra imediatamente após iniciar.

    **Causa:** Nenhuma chave de API foi configurada no `.env`.

    **Solução:**

    1. Crie ou abra o arquivo `.env` no diretório onde você executa o `chatcli` (ou no `HOME`)
    2. Adicione as credenciais para pelo menos um provedor:
    ```env
    LLM_PROVIDER=OPENAI
    OPENAI_API_KEY="sk-sua-chave-secreta-aqui"
    ```
    3. Salve e execute `chatcli` novamente
  </Accordion>

  <Accordion title="Alterações no .env não têm efeito" icon="rotate">
    **Sintomas:** Você alterou o `LLM_PROVIDER` ou outro valor, mas o ChatCLI usa a configuração antiga.

    **Causa:** O ChatCLI carrega as configurações na inicialização.

    **Solução:** Use o comando `/reload` dentro do modo interativo para recarregar as variáveis instantaneamente.

    ```bash
    /reload
    ```
  </Accordion>

  <Accordion title="@file não encontra um arquivo/diretório" icon="file-circle-exclamation">
    **Sintomas:** Erro "o arquivo não existe" ou "caminho não encontrado".

    **Solução:**

    - **Caminhos Relativos** — são relativos ao diretório onde você executou o `chatcli`. Ex: `@file ./project/src/main.go`
    - **Home (`~`)** — funciona como atalho: `@file ~/documentos/notas.txt`
    - **Permissões** — verifique com `ls -l` se você tem permissão de leitura no arquivo
  </Accordion>

  <Accordion title="Modo Agente não executa nada" icon="robot">
    **Sintomas:** A IA apresenta um plano de ação, mas apenas aguarda sem executar.

    **Causa:** Isso é o comportamento esperado! O Modo Agente exige aprovação explícita.

    **Solução:**

    - Digite o **número** do comando (ex: `1`) para executá-lo individualmente
    - Digite `a` para executar **todos** os comandos em sequência
    - Use `--agent-auto-exec` no modo one-shot para execução automática de comandos seguros
  </Accordion>

  <Accordion title="Provedor Ollama não é detectado" icon="server">
    **Sintomas:** Mesmo com `OLLAMA_ENABLED=true`, o provedor não aparece disponível.

    **Solução:**

    1. **Servidor Ollama** — confirme que está rodando: `ollama serve`
    2. **Modelo baixado** — verifique com `ollama list`. Se vazio, baixe um: `ollama pull llama3`
    3. **URL Base** — se não está no endereço padrão, defina no `.env`:
    ```env
    OLLAMA_BASE_URL="http://localhost:11434"
    ```
  </Accordion>

  <Accordion title="Respostas cortadas ou incompletas" icon="scissors">
    **Sintomas:** A resposta da IA para no meio de uma frase.

    **Causa:** O limite de tokens da resposta foi atingido.

    **Solução:** Aumente o `MAX_TOKENS` do seu provedor no `.env`:

    ```env
    OPENAI_MAX_TOKENS=60000
    ANTHROPIC_MAX_TOKENS=20000
    GOOGLEAI_MAX_TOKENS=50000
    ```
  </Accordion>

  <Accordion title="Timeout em chamadas de API" icon="clock">
    **Sintomas:** Erro de timeout ou a aplicação trava aguardando resposta.

    **Solução:**

    - Use `--timeout` para definir um limite: `chatcli -p "pergunta" --timeout 60s`
    - Configure `MAX_RETRIES` e `INITIAL_BACKOFF` no `.env` para retentativas automáticas
    - Considere configurar [Fallback de Provedores](/pt/providers/provider-fallback) para redundância
  </Accordion>

  <Accordion title="Agent precisa criar arquivo temporário e o /coder bloqueia">
    O modo `/coder` valida que toda escrita ocorra dentro do diretório do projeto. A partir desta versão, o ChatCLI cria um [Workspace de Sessão](/pt/context/session-workspace) em `$TMPDIR/chatcli-agent-<random>/` que está automaticamente na allowlist:

    ```xml
    <tool_call name="@coder" args='{"cmd":"exec","args":{"cmd":"cat > $CHATCLI_AGENT_TMPDIR/script.sh <<EOF\n...\nEOF\nbash $CHATCLI_AGENT_TMPDIR/script.sh"}}' />
    ```

    Para escritas via `write` ou `patch`, use o caminho absoluto que aparece no system prompt (a variável `$CHATCLI_AGENT_TMPDIR` não é expandida no campo `file`).

    Cleanup automático no exit; defina `CHATCLI_AGENT_KEEP_TMPDIR=true` para preservar e inspecionar.
  </Accordion>

  <Accordion title="Tool result truncado mas não consigo ver o conteúdo completo">
    Quando o orçamento corta o output e mostra `[full output saved to /tmp/chatcli-agent-XXX/tool-results/...]`, o caminho está na allowlist de leitura do agente. Basta abrir com `read_file`:

    ```xml
    <tool_call name="@coder" args='{"cmd":"read","args":{"file":"/tmp/chatcli-agent-XXX/tool-results/budget_tc_3_1.txt","start":1200,"end":1500}}' />
    ```

    Não refaça a tool call original — o conteúdo já está em disco. Detalhes em [Resultados de Tools](/pt/context/tool-result-management).
  </Accordion>

  <Accordion title="Endpoint /metrics ou log enorme satura o contexto">
    Duas estratégias complementares:

    1. **Filtros do `@webfetch`** — passe `filter`, `exclude`, `from_line`/`to_line` para filtrar antes do truncamento, ou `save_to_file: true` para persistir o corpo no scratch dir e ler trechos com `read_file`. Ver [Web Tools](/pt/tools/web-tools#filtros-para-payloads-grandes).
    2. **Delegação para subagente** — `delegate_subagent` executa a análise em janela de contexto isolada e devolve só o resumo. Ver [Subagent Delegation](/pt/agents/subagent-delegation).
  </Accordion>

  <Accordion title="Subagente recusa rodar com erro 'subagent depth N exceeds maximum'">
    Você atingiu o limite de delegação aninhada (default 2). Causa comum: um subagente que delega para outro subagente em loop. Aumente com cuidado:

    ```bash
    CHATCLI_AGENT_SUBAGENT_MAX_DEPTH=3 chatcli
    ```

    Mas considere se a tarefa não cabe melhor em uma única delegação com `prompt` mais explícito sobre o que precisa ser feito.
  </Accordion>

  <Accordion title="O vault da memória não mostra uma mudança, ou lista notas como preservadas" icon="book">
    O [vault](/pt/context/knowledge-graph) (`~/.chatcli/vault`) é uma projeção de mão única da memória: ele sincroniza em background cerca de 5 segundos depois de uma mudança na memória (no máximo 60 segundos sob um fluxo contínuo de mudanças), e o que você edita lá nunca volta para a memória.

    - `/memory vault status` mostra o diretório e a última sincronização; `/memory vault sync` sincroniza agora.
    - Notas **preservadas** são as que você editou à mão, ou arquivos que o chatcli nunca gravou: elas nunca são sobrescritas. `/memory vault sync --force` regenera as notas do próprio chatcli (suas edições nelas se perdem); um arquivo que o chatcli nunca gravou é preservado mesmo assim.
    - Nada aparece: confira `CHATCLI_MEMORY_VAULT` (um valor falso o desliga; `/memory vault sync` ainda grava sob demanda) e `CHATCLI_MEMORY_VAULT_DIR`.
  </Accordion>

  <Accordion title="Um link que eu criei sumiu, ou o unlink diz que as notas se ligam pelos dados" icon="link-slash">
    - Um link criado com `@memory link` ou `/memory link` para um fato que depois foi substituído acompanha o fato que tomou o lugar dele.
    - Um link cuja nota não existe mais (um fato esquecido, um contexto apagado) fica guardado enquanto a nota falta e é removido pela compactação da memória depois de 30 dias sem ela.
    - `/memory unlink` remove só os links que você criou. Links que vêm dos próprios dados — o projeto ou as tags de um fato, os fatos de um tópico, um `[[wikilink]]`, um nome citado no texto — são listados em vez disso; mude esses dados para mudar o link.
  </Accordion>
</AccordionGroup>

## Dados cifrados: proteger e recuperar

Suas sessões, sua memória e os outros dados locais são [cifrados em repouso](/pt/security/encryption-at-rest) por padrão. Com criptografia, a chave importa: estes cenários mostram como não perder o acesso e como recuperá-lo.

<Warning>
**Três regras que evitam quase toda perda:**
1. Rode `/config security recovery-key` uma vez e guarde a chave num gerenciador de senhas.
2. Nunca edite nem apague arquivos em `~/.chatcli` à mão para "consertar" um erro, e nunca apague o item `chatcli` / `auth-key` do keychain do sistema nem os arquivos `~/.chatcli/.auth-key*`.
3. Faça backup de `~/.chatcli` como de qualquer outro dado. Um backup só serve junto com a chave de recuperação, então guarde os dois separados.
</Warning>

<AccordionGroup>
  <Accordion title='"encrypted at rest but CHATCLI_ENCRYPTION_KEY is not set" ou "Stores travados"' icon="lock">
    **Causa:** o ChatCLI não conseguiu ler a chave. O erro diz o motivo, por exemplo um keychain do macOS travado numa sessão SSH, ou um Linux com `secret-tool` mas sem sessão de desktop. O `/config security` mostra `indisponível` com o motivo.

    **O que acontece enquanto isso:** nada se perde. Os stores da memória que não abrem ficam travados em somente leitura, para nada sobrescrevê-los, e as sessões falham ao carregar em vez de carregar vazias.

    **Solução:** destrave o keychain (entre no desktop, ou `security unlock-keychain` no macOS) e rode o ChatCLI de novo. Onde nunca há keychain, defina `CHATCLI_ENCRYPTION_KEY` com a sua chave de recuperação.
  </Accordion>

  <Accordion title="Máquina nova, sistema reinstalado ou keychain resetado" icon="laptop">
    A chave padrão ficava no keychain antigo. Copie o `~/.chatcli` para a máquina nova e depois:

    ```bash
    export CHATCLI_ENCRYPTION_KEY="<chave de recuperação>"
    ```

    Tudo abre. Depois rode `/config security use-keychain`: seus dados passam para a chave do keychain da máquina nova, e você pode remover a variável.

    Com um arquivo de recuperação, um único comando faz as duas coisas: `/config security recovery-key --restore <arquivo>` (ele pede a senha do arquivo).

    **Sem chave de recuperação e sem o keychain antigo, os stores cifrados não podem ser recuperados.** É para isso que serve a criptografia. Exportações feitas antes (`/session export`, `/memory export`) estão em texto puro e continuam importando.
  </Accordion>

  <Accordion title='Cron, SSH ou contêiner: "a chave de credenciais desta instalação mora no keychain do sistema"' icon="clock">
    Depois que a chave vai para o keychain, o ChatCLI se recusa a criar uma nova num contexto que não alcança o keychain, porque uma chave nova deixaria seus dados órfãos. Dê a chave a esse contexto:

    ```bash
    CHATCLI_ENCRYPTION_KEY="<chave de recuperação>" chatcli -p "..."
    ```

    Não apague `~/.chatcli/.auth-key.keychain` para o erro sumir: é ele que impede a criação de uma segunda chave.
  </Accordion>

  <Accordion title="Voltando para uma versão anterior do ChatCLI" icon="clock-rotate-left">
    Versões anteriores não leem stores cifrados. Com a versão **nova**, primeiro regrave tudo em texto puro:

    ```bash
    export CHATCLI_ENCRYPTION_KEY=off
    chatcli    # depois rode: /config security reseal
    ```

    Então instale a versão anterior. Mantenha `CHATCLI_ENCRYPTION_KEY=off` se voltar a usar a nova.
  </Accordion>

  <Accordion title="Desligando a criptografia" icon="toggle-off">
    `export CHATCLI_ENCRYPTION_KEY=off` para de cifrar os dados novos. Os dados já cifrados continuam abrindo. Para decifrar também o que existe, rode `/config security reseal` com ela desligada. Para só ler um arquivo, use `/config security reveal <arquivo>`: nada muda no disco.
  </Accordion>

  <Accordion title="Um backup restaurado trouxe de volta um .auth-key antigo" icon="box-archive">
    Depois que a chave vai para o keychain, um arquivo de chave que apareça depois é ignorado em favor da chave do keychain, com um aviso. Nada é sobrescrito. Remova o `~/.chatcli/.auth-key` avulso depois de confirmar que o `/config security` mostra a chave do keychain.
  </Accordion>

  <Accordion title="Editei um arquivo cifrado, ou um arquivo está danificado" icon="file-circle-xmark">
    Arquivos cifrados são autenticados: um byte alterado faz o arquivo inteiro não abrir. O ChatCLI nunca o trata como vazio e nunca o sobrescreve.

    - Restaure esse arquivo de um backup.
    - As notas diárias são a exceção que dá para editar: uma nota salva em texto puro à mão continua sendo lida e é cifrada de novo na próxima gravação.
    - Para ler ou mudar seus dados fora do ChatCLI, exporte antes (`/session export`, `/memory export`, `/context export`). Para ler a memória e os contextos como notas, abra o [vault da memória](/pt/context/knowledge-graph) (`~/.chatcli/vault`), mantido em texto puro para isso.
  </Accordion>

  <Accordion title='"the OS keychain holds a different credential key than ~/.chatcli/.auth-key"' icon="key">
    **Causa:** o keychain do sistema já tem um item `chatcli` / `auth-key` que não é a sua chave (muitas vezes deixado por um build antigo ou por uma execução de testes), enquanto a sua chave real é o arquivo `~/.chatcli/.auth-key`. O ChatCLI nunca sobrescreve uma chave do keychain no palpite, então continua usando o arquivo: seus dados, credenciais e chave de recuperação não são afetados.

    **Solução:** rode `/config security use-keychain`. Ele só move a chave do arquivo para o keychain depois de conferir que ela abre o seu store de credenciais e os seus dados cifrados (sem store de credenciais, porque você nunca fez login, os dados cifrados sozinhos são a prova), guarda o valor anterior do keychain como `auth-key.previous` e lê a chave de volta antes de remover o arquivo. A chave em si não muda, e o aviso some.
  </Accordion>

  <Accordion title="Trocando CHATCLI_KEYCHAIN_BACKEND entre keychain e file" icon="key">
    Seguro nos dois sentidos: a chave é a mesma, só muda onde ela fica guardada. Mudar para `file` copia a chave do keychain para `~/.chatcli/.auth-key` (modo `0600`) e mantém o item do keychain; voltar para `keychain` ou `auto` usa o keychain de novo. O único ponto de atenção é que, com `file`, a chave fica em disco ao lado dos dados.
  </Accordion>

  <Accordion title="Usando os mesmos dados em duas máquinas" icon="arrows-left-right">
    A chave do keychain pertence a uma máquina. Defina a mesma `CHATCLI_ENCRYPTION_KEY` nas duas (por exemplo a chave de recuperação da primeira), rode `/config security reseal` uma vez em cada e copie ou sincronize o `~/.chatcli` entre elas.
  </Accordion>
</AccordionGroup>
