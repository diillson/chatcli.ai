---
title: "Capacidade de Analytics"
openapi: "GET /analytics/capacity"
description: "Retorna um relatório de capacidade de requests versus limits para Deployments que tiveram incidentes"
icon: "server"
---

<ParamField query="namespace" type="string">
  Filtrar por namespace Kubernetes. Sem ele, cobre todos os namespaces.
</ParamField>

<ParamField query="from" type="string">
  Início da janela, RFC 3339.
</ParamField>

<ParamField query="to" type="string">
  Fim da janela, RFC 3339. A **duração** da janela é `to − from` quando os dois são válidos, senão 7 dias; a janela sempre termina no horário atual.
</ParamField>

Role mínima: `viewer`. Uma previsão é gerada para cada recurso distinto referenciado por um Issue (qualquer Issue, não só os da janela). O planner lê o recurso como um **Deployment** com esse nome; recursos que não são Deployments, ou que não existem mais, são ignorados silenciosamente.

## Campos da previsão

| Campo | Descrição |
|-------|-----------|
| `Resource` | O recurso apontado pelos Issues (`kind`, `name`, `namespace`) |
| `CurrentUsage` | Requests do primeiro container, usados como aproximação do uso (`CPUMillicores`, `MemoryBytes`); não são métricas ao vivo |
| `Limits` | Limits do primeiro container |
| `UsagePercentage` | `CurrentUsage / Limits × 100` para `CPU` e `Memory` |
| `Trend` | `Direction` é `insufficient_history` e as inclinações por dia são `0`: o operator não guarda histórico de uso para ajustar uma tendência |
| `Forecast` | Um texto `Recommendation`; as datas de esgotamento vêm `null` e as contagens de dias `0`, já que nenhuma data de esgotamento é projetada |
| `IncidentCorrelation` | Issues do namespace dentro da janela, quantos apontam para este recurso, e `ResourceIsBottleneck` (mais de 2) |
| `UsageSource` | De onde vem o `CurrentUsage`: sempre `requests` |
| `HistoryAvailable` | Sempre `false`: nenhuma amostra de uso é coletada |
| `Urgency` | `plan` quando os requests chegam a 80% dos limits ou o recurso é um gargalo, `none` nos demais casos |

A recomendação alerta quando os requests passam de 80% dos limits, depois aponta incidentes repetidos em um recurso gargalo e, fora isso, diz que nenhuma tendência pode ser projetada e que os requests estão dentro dos limits.

<Warning>
Este é um relatório de requests versus limits com correlação de incidentes, e não uma previsão: o uso é o que o primeiro container pede em requests, e não consumo medido, e nenhuma tendência ou data de esgotamento é projetada.
</Warning>

<Note>
A previsão é uma struct Go sem tags JSON, então as chaves vêm em **PascalCase** (só `Resource` mantém as chaves internas em minúsculas). Datas de esgotamento ausentes vêm `null` e contagens de dias ausentes vêm `0`.
</Note>
