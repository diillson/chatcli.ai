Os dois endpoints ficam na **raiz** do servidor da API REST — `http://<operator-host>:8090/healthz` e `/readyz`, **não** em `/api/v1` — e não exigem API key. Eles informam o estado do próprio servidor da API REST.

<Note>
Estes **não** são os endpoints que o Kubernetes consulta. As probes de liveness e readiness do Deployment do operator usam os endpoints do controller-runtime `/healthz` e `/readyz` na porta de health **8081** (value `health.port` do chart), que só verificam se o processo do manager está vivo. Use os endpoints da 8090 abaixo para monitorar a API de fora.
</Note>

## Verificação de Liveness

```
GET /healthz
```

Sempre retorna `200 OK` enquanto o servidor da API REST estiver atendendo. Nenhuma autenticação necessária.

<ResponseExample>
```json Response 200 — /healthz
{
  "status": "ok",
  "timestamp": "2026-03-19T15:00:00Z"
}
```
</ResponseExample>

## Verificação de Readiness

```
GET /readyz
```

Lista Issues pela API do Kubernetes (limite 1, timeout de 5 segundos). Retorna `200 OK` quando isso funciona e `503 Service Unavailable`, com o texto do erro em `status`, quando falha (API server inacessível, RBAC faltando, CRD não instalado).

<ResponseExample>
```json Response 200 — /readyz
{
  "status": "ready",
  "timestamp": "2026-03-19T15:00:00Z"
}
```
</ResponseExample>

<ResponseExample>
```json Response 503 — /readyz
{
  "status": "not ready: context deadline exceeded",
  "timestamp": "2026-03-19T15:00:00Z"
}
```
</ResponseExample>
