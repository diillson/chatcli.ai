The **`@browser`** tool drives a **real local Chrome/Chromium** browser so the agent can **see and interact with web pages** the way a person would: open a URL, read the rendered page as text (shadow DOM and same-origin iframes included), **find** text on it, click with a **real mouse**, type into inputs **and rich-text editors**, run JavaScript, capture screenshots **it then looks at**, read **response bodies**, list **downloads**, and inspect the page's **console** and **network** activity. When a site puts up a **bot challenge** (Cloudflare, a captcha), the tool says so instead of pretending the block page is the content, and hands the window to you.

It is the **verification loop** for web work — the agent builds or changes a frontend, then **actually looks at it** and debugs it from what the page logged and requested, instead of guessing from source.

<Info>
`@browser` speaks the **Chrome DevTools Protocol (CDP)** directly over the websocket client ChatCLI already ships — **zero new dependency**, no driver, no downloaded runtime, no API key. It only needs a **locally installed Chromium-family browser** (Google Chrome, Chromium, Brave or Edge).
</Info>

## How it works

```text
@browser open http://localhost:3000
        │
        ▼
launch a headless Chrome (first use) — reused for the whole session
        │
        ▼
attach over CDP (websocket) → navigate → wait for load
        │
        ▼
snapshot: title, URL, NUMBERED interactive elements, visible text
        │
        ▼
click [n] / type [n] "text" → snapshot again → console / network to debug
        │
        ▼
close (or it dies automatically when ChatCLI exits)
```

1. **Lazy launch** — the first `open` starts one browser; every later command reuses that **single stateful session**.
2. **CDP over websocket** — navigation, DOM reads, screenshots and event capture all flow over the DevTools websocket. No Selenium/Playwright, no external binary.
3. **Snapshot as text** — the page is rendered to model-friendly text with every interactive element **stamped and numbered** (with its state: value, checked, disabled, expanded…) so the agent can address them precisely. The scan reaches **into open shadow roots and same-origin iframes**; cross-origin frames are listed so the agent knows a captcha or an embedded login lives there. **Password fields never show their value.**
4. **Continuous capture** — console messages (errors included) and network responses are captured into bounded rings, so you can ask "what did the page log?" **after the fact**.
5. **Visible on demand** — the browser is headless by default, but the agent can put the window **on your screen** with `show` (or `open --visible`) whenever *you* need to act — log in, pick an account, solve a captcha — then take it back with `hide`. The switch relaunches the browser **on the same profile**, so cookies and logins survive it.
7. **Looks like the browser it is** — a headless session presents the same user agent, client hints, language and a laptop-sized viewport as the headed browser would, so sites serve it their normal page instead of a block page for "HeadlessChrome".
6. **Dies with the session** — a browser ChatCLI launched never outlives it; it is closed on CLI shutdown (or explicitly with `close`).

## Subcommands

Invoke with a JSON envelope `{cmd, args}` or the flat argv form. The model calls `@browser` automatically in `/agent` and `/coder` when it needs to look at a page.

| Subcommand | What it does | Key args |
|:-----------|:-------------|:---------|
| `open` | Navigate to a URL (launches the browser on first use) and return a **page snapshot** | `url` (req.), `--visible` |
| `show` | Make the window **visible on your screen** (relaunches a headless session on the same profile — logins kept); optionally navigates | `url` (optional) |
| `hide` | Back to headless; the window disappears, the session and its cookies stay | — |
| `wait` | Block until the page reaches a state: URL contains, text contains, an element exists, the URL **changes**, a **bot challenge is gone** and/or the **network is quiet** — the hand-off after `show` | `--url`, `--text`, `--selector`, `--changed`, `--unblocked`, `--idle`, `--timeout` (120s, max 600s) |
| `snapshot` | The current page as text: title, URL, numbered interactive elements with their state, visible text (iframes included) | `--max N` (cap text length), `--offset N` (continue a long text) |
| `text` | The **plain visible text** of the page or of one element, **paged** — the way to read a long article in full | `target` (optional), `--offset N`, `--max N` |
| `find` | **Locate text on the page**: matching interactive elements (with `[n]` refs) and every occurrence in the text with context — before scrolling or guessing selectors | `text` (req.), `--max N` |
| `click` | **Real mouse click** on an element by its **`[n]` ref** from the last snapshot **or** a CSS selector; `--count 2` double-clicks, `3` selects a word; `--button right` opens a context menu | `target` (req.), `--count`, `--button` |
| `type` | Type into an input, textarea **or rich-text editor** (contenteditable); replaces the content unless `--append`; `--submit` presses Enter / submits the form | `target` (req.), `text`, `--append`, `--submit` |
| `clear` | Empty an input, textarea or editor | `target` (req.) |
| `press` | Send a key to the focused element: `Enter`, `Tab`, `Escape`, `ArrowDown`, a character, or a chord like `Control+a` | `key` (req.) |
| `hover` | Move the mouse over an element (opens hover menus and tooltips) | `target` (req.) |
| `select` | Choose a `<select>` option by value or visible text | `target` (req.), `value` |
| `upload` | Attach local file(s) to an `<input type=file>` — the OS picker never opens under automation | `target` (req.), `file` / `files` |
| `scroll` | Move the viewport | `down` · `up` · `top` · `bottom` · `--to target` |
| `eval` | Run JavaScript in the page and return its value — in **REPL mode**, so a `const` declared by one call can be declared again by the next and top-level `await` works | `javascript` (req.) |
| `screenshot` | Capture the viewport — or the **whole page** with `--full` — as **PNG** and **attach it to the conversation** so the model sees it on the next turn | `--file name`, `--full`, `--view false` (only save) |
| `html` | The `outerHTML` of an element (or the document) for markup debugging | `target` (optional), `--max N` |
| `pdf` | Save the page as **PDF** (headless only) | `--file path` (optional) |
| `resize` | Emulate a viewport (`--mobile` also enables touch) to verify responsive layouts | `width`, `height`, `--mobile` |
| `tabs` | List open tabs — popups such as OAuth windows show up here | — |
| `tab` | Switch to tab *n* from the `tabs` list | `n` (req.) |
| `cookies` | List cookies (**names and domains only, never values**) to check whether a login stuck; `--clear` logs out of everything | `domain` (optional), `--clear` |
| `console` | The captured console messages (errors and auto-accepted dialogs included) | `--tail N` |
| `network` | The captured network responses: method, status, URL; `--filter` keeps URLs containing a substring and `--body` returns the **body** of the newest match (the JSON an API call answered, for instance) | `--tail N`, `--filter substr`, `--body` |
| `downloads` | The files the page downloaded during this session and where they were saved (the session scratch directory, never your Downloads folder) | — |
| `back` / `forward` / `reload` | History navigation and reload | — |
| `status` | Whether a session is running, **visible or headless**, which profile it uses and what page it is on | — |
| `close` | Close the browser session — on a throwaway profile the logins made in it are gone, and the result says so | — |

## Refs vs. CSS selectors

Every `snapshot` stamps each interactive element with a `data-chatcli-ref` attribute and returns a **numbered listing**. `click` and `type` accept **either** that `[n]` ref number **or** a raw CSS selector:

```text
Interactive elements (use the [n] ref with click/type):
[1] <a> Docs -> /docs
[2] <input> Search type=search
[3] <input> Password type=password value=<hidden>
[4] <button> Sign in
[5] <div> Write a comment… editable
[6] <button> Submit in iframe "https://embed.example.com/widget"

@browser click 4          # by ref (recommended — no guessing at selectors)
@browser click #login-btn # by CSS selector
@browser click 4 --count 2     # double-click; --count 3 selects a word/line
@browser click 4 --button right
```

Each line carries the element's **label** the way an accessibility tree would resolve it (`aria-label`, `<label for>`, placeholder, alt text…) and its **state**: the current value, `checked`/`unchecked`, `disabled`, `expanded`/`collapsed`, `selected`, the `role`, and `in iframe` when it lives in an embedded frame. A password field shows `value=<hidden>` — its value never reaches the transcript, and what the agent types into one is not echoed either.

`click` sends **real mouse events** at the element's center (the page sees `mousedown`/`mouseup`/`click` like a person's click, which React synthetic handlers, maps and drag-and-drop widgets need). When the center is covered by another element — a sticky header, a modal, a cookie banner — the click is dispatched programmatically instead and the result says what covered it.

`type` sets the value of inputs and textareas through the native setter (frameworks see the change) and inserts text into **rich-text editors** (`contenteditable`: LinkedIn, Slack, Notion, ProseMirror, Draft.js…) through the browser's input pipeline, so the editor receives `beforeinput`/`input` like a keystroke and its Send button enables. `--append` keeps what was there; `clear` empties it.

<Note>
Refs are stable **until the next navigation**. After you `open` a new URL or a `click` triggers navigation, take a fresh `snapshot` before addressing elements by `[n]` again.
</Note>

## Reading a long page

A snapshot caps the page text (12 KB by default) so a busy page never floods the context. Nothing is lost: the cap is a **window**, and the tool tells the agent how to move it.

```text
@browser text --offset 12000            # continue where the snapshot stopped
@browser text article --max 30000       # the text of one element, bigger window
@browser find "refund policy"           # where is it? refs + text occurrences with context
  → Interactive elements matching "refund policy":
    [17] <a> Refund policy -> /help/refunds
    Text matches for "refund policy" (2 shown of 2):
    …see our [refund policy] before ordering… (at byte 8120)
```

`find` is the first move on an unfamiliar page: it stamps refs exactly like `snapshot`, so the `[n]` it returns is clickable right away, and it searches the **whole** text, including what the snapshot window did not show. Every result ends with a range footer (`[text bytes 0–12000 of 48210; --offset 12000 continues]`), so the agent reads the page in order instead of guessing with `eval`.

`eval` runs in the DevTools **REPL mode**: `const data = …` in one call and `const data = …` again in the next is fine (no "Identifier has already been declared"), and `await fetch(…)` works at the top level.

## Bot challenges and block pages

Some sites answer a first visit with an interstitial — Cloudflare's "Just a moment…", a captcha, a "Press & Hold", an "Access denied" — instead of the page. `@browser` recognizes the common ones (Cloudflare, reCAPTCHA, hCaptcha, PerimeterX/HUMAN, DataDome, Imperva, Akamai, AWS WAF, and generic access-check pages by their title and text) and reports them **as what they are**:

```text
@browser open https://example.com/pricing
  → ⚠ Bot challenge detected (Cloudflare): this page is the interstitial, not
    the content you asked for. Automation cannot pass it — `show` the window
    so the user solves it, then `wait --unblocked` (the URL usually does not
    change) and read the page again.
```

`open` first waits a few seconds for a challenge that clears by itself (a managed challenge often does in a real browser), and only then reports it. The hand-off is the same as for a login:

```text
@browser show                       # the window appears with the challenge
  (the user solves it)
@browser wait --unblocked --timeout 300
  → Condition met after 14s: Pricing — Example (https://example.com/pricing)
@browser hide
@browser text
```

`wait --unblocked` fires when no challenge is showing — the right condition here, since a challenge page keeps the URL of the page it protects, so `--url` and `--changed` never fire. `find` and `snapshot` carry the same warning as long as the block page is up, so the agent never mistakes it for content. A captcha widget on a normal form (a sign-up page, say) is **not** reported as a block: it is just one more element, and it lives in a cross-origin iframe the snapshot lists.

<Note>
This is detection and a polite hand-off, not evasion. The headless session identifies itself as the browser it is (a real Chrome, headless marker removed, your language, a laptop viewport), which is what a normal visit looks like; a site that refuses automated browsers outright still refuses it, and the agent tells you so.
</Note>

## Network bodies and downloads

`network` lists what the page requested. With `--filter` it keeps only URLs containing a substring, and with `--body` it returns the **body** of the newest match — the JSON an API call answered, the HTML of a fragment, the error page behind a 500:

```text
@browser network --filter /api/ --body
  → Last 2 network response(s):
    201 POST http://localhost:3000/api/subscribe (Fetch)
    500 POST http://localhost:3000/api/send (Fetch)

    Body of 500 POST http://localhost:3000/api/send:
    {"error":"SMTP connection refused"}
```

Bodies are capped (8 KB by default, `--max` raises it), binary bodies are described rather than dumped, and they are only available while the page that received them is still loaded.

Files the page downloads — a report, an export, a PDF behind a button — are saved in the **session scratch directory** (the same place screenshots go), never in your Downloads folder, and `downloads` lists them with their state and path so the agent can hand them to `@view` or `@coder read`. An attached browser (`CHATCLI_BROWSER_CDP_URL`) keeps its own download settings.

## Let the user log in (visible hand-off)

The agent's browser starts as a **throwaway profile**: none of the sessions in your everyday Chrome exist there. So when a task hits a login wall, the agent hands the window to you instead of guessing credentials:

```text
# The agent surfaces the login page on your screen
@browser show https://app.example.com/login
  → Browser window is now VISIBLE on the user's screen. They can log in or
    interact directly; the session (cookies, logins) is shared with you…

# …and waits until the page reaches the post-login URL (up to 5 minutes)
@browser wait --url /dashboard --timeout 300
  → Condition met after 42s: Dashboard (https://app.example.com/dashboard)

# Window goes away; the authenticated session keeps working headless
@browser hide
@browser snapshot
```

`wait` accepts `--url`, `--text`, `--selector`, `--changed`, `--unblocked` and `--idle` (all must hold when combined). `--changed` fires when the URL leaves the one it had when the wait started — the right condition when the landing page cannot be predicted (GitHub, for instance, ignores the login's `return_to` and lands on its home page). A timeout is reported as a result, including where the page moved from if it did move, so the agent can ask you or wait again. Without a page condition to wait for, the agent asks you directly with [`@ask`](/coder/interactive-ask). Logins done this way live for the **rest of the ChatCLI session**; to keep them across runs, set `CHATCLI_BROWSER_PROFILE` (below).

<Tip>
OAuth providers often open the sign-in flow in a **popup**. `tabs` lists it and `tab 2` lets the agent drive it — or you finish it yourself in the visible window.
</Tip>

<Note>
**Signing in with Google.** Google refuses password sign-in in browsers it detects as automated ("This browser or app may not be secure"). ChatCLI launches Chrome with the automation marker off (`navigator.webdriver` is `false`), which is what that check looks at. If Google still refuses, sign into the site with a password or passkey instead of the Google button, or attach ChatCLI to the Chrome you are already signed into with `CHATCLI_BROWSER_CDP_URL` (below).
</Note>

If you **close the tab or the window** while the agent is waiting, `wait` reports it instead of failing, and the next `open`/`show` attaches a fresh tab — the browser session itself keeps running.

## A worked example

Build a page in `/coder`, then verify it end to end:

```text
# 1) Open the app the coder just started
@browser open http://localhost:3000
  → Page: My App — Home
    Interactive elements:
      [1] link   "Products"
      [2] input  "Email"      (type=email)
      [3] button "Subscribe"

# 2) Fill the form and submit
@browser type 2 "user@example.com"
@browser click 3

# 3) See what happened
@browser snapshot
  → Page: My App — Thanks!
    "You're subscribed."

# 4) Something looked off? Debug from the page itself
@browser console --tail 20
  → [error] Uncaught TypeError: cannot read 'id' of undefined (app.js:42)

@browser network --tail 10
  → 500 POST http://localhost:3000/api/subscribe (Fetch)
```

The agent now knows the button worked in the UI but the backend returned **500**, and the exact console error — the full verify-and-fix loop without leaving ChatCLI.

## Environment variables

| Variable | Description | Default |
|:---------|:------------|:--------|
| `CHATCLI_BROWSER_BIN` | Path to the browser binary to use | auto-detect Chrome/Chromium/Brave/Edge |
| `CHATCLI_BROWSER_HEADLESS` | Run headless (`true`) or open a **visible window** (`false`) for the whole session — `show`/`hide` switch per call regardless | `true` |
| `CHATCLI_BROWSER_PROFILE` | Where cookies and logins live. Unset = throwaway profile deleted on close. `true` = a persistent profile owned by ChatCLI under `~/.chatcli/browser/profile`; a path = that directory. Never your everyday Chrome profile | _(throwaway)_ |
| `CHATCLI_BROWSER_CDP_URL` | **Attach to a browser you already have open** instead of launching one — `http://127.0.0.1:9222` (start Chrome with `--remote-debugging-port=9222`) or a `ws://` DevTools URL. ChatCLI opens one tab of its own there and closes only that tab on exit; the window is yours, so it is always visible and never killed | _(launch own browser)_ |

```bash
# Watch the agent drive a real window for the whole session
export CHATCLI_BROWSER_HEADLESS=false

# Keep logins between ChatCLI runs (profile owned by ChatCLI)
export CHATCLI_BROWSER_PROFILE=true

# Use the Chrome you are already signed into
# (launch it once with: google-chrome --remote-debugging-port=9222)
export CHATCLI_BROWSER_CDP_URL=http://127.0.0.1:9222

# Point at a specific browser
export CHATCLI_BROWSER_BIN="/Applications/Brave Browser.app/Contents/MacOS/Brave Browser"
```

## Security

Observation commands are **read-only** and skip the confirmation prompt — the agent can look freely: `open`, `show`, `hide`, `wait`, `snapshot`, `text`, `find`, `screenshot`, `html`, `pdf`, `resize`, `tabs`, `tab`, `cookies` (listing), `console`, `network` (bodies included), `downloads`, `scroll`, `back`, `forward`, `reload`, `status`, `close`.

Commands that **act** on a page — `click`, `type`, `clear`, `press`, `hover`, `select`, `upload`, `eval` and `cookies --clear` — can trigger real actions on remote sites (or log you out of everything), so they go through the standard **security gate** like any other mutating tool. See [Coder Mode Security](/coder/coder-security).

`cookies` never returns cookie **values**: the agent can tell that a session cookie exists for a domain, but a token never lands in the transcript. **Password fields** show `value=<hidden>` in every snapshot, and what the agent types into one is not echoed back — still, the right way to enter *your* password is in the visible window, yourself.

<Warning>
`@browser` drives a real browser signed into whatever profile it runs on. The default throwaway profile is the safe choice for untrusted pages; a persistent profile (`CHATCLI_BROWSER_PROFILE`) or your own browser (`CHATCLI_BROWSER_CDP_URL`) hands the agent every login stored there — treat `click`/`type`/`eval` on external sites as the side-effecting operations they are.
</Warning>

## Notes

- **One session per process**, launched lazily on the first `open` and reused across every call.
- Console and network are captured **continuously** into bounded rings — `console`/`network` read the recent history, they don't need to be "armed" first.
- `screenshot` writes a PNG in the session scratch directory (`--file name` names it there) **and attaches it to the conversation** through the same vision pipeline as [`@view`](/usage/vision-input), so the model sees what it captured on the next turn without a second call. `--view false` only saves the file; outside an agent loop (`chatcli tool @browser screenshot`) the result is just the path.
- A snapshot that starts with **"Bot challenge detected"** is the block page, not the content — see above. The agent is told never to retry `open` in a loop against it.
- `alert()`, `confirm()` and `prompt()` dialogs are **accepted automatically** (they would otherwise freeze the page) and traced in `console` as `[dialog]` entries.
- A browser ChatCLI launched is **always** closed on ChatCLI shutdown; a stray headless Chrome never survives the session. An attached browser (`CHATCLI_BROWSER_CDP_URL`) only loses the tab ChatCLI opened.
